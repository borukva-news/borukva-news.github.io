# Borukva News — Node.js / Express + React port

Це переписаний на **Node.js (Express) + React (SPA)** порт оригінального
Flutter-застосунку [`borukvanews.github.io`](https://github.com/PsProfi/borukvanews.github.io).

Оригінал був Flutter/Dart-застосунком, задеплоєним на GitHub Pages. Тут та
сама функціональність відтворена на звичайному веб-стеку:

- **`server/`** — Express-сервер. Віддає React-білд, статичні ассети
  (`/assets/...`) і проксіює запити до GitHub Contents API для
  збереження/читання "хотспотів" (клікабельних зон на сторінках газети).
  Це заміна Cloudflare Worker (`gh-proxy/github-proxy.js`) з оригіналу.
- **`client/`** — React SPA (Vite + react-router-dom). Один-в-один повторює
  маршрути з `go_router` (`lib/main.dart`) та логіку всіх екранів.
- **`shared-assets/`** — шрифти, звук, фонові зображення (вже додані).
  **Теки з газетними сторінками (300+ МБ) сюди не включені** — див. нижче.

## 1. Додайте великі ассети (газетні сторінки)

Це єдине, що потрібно ручками перенести з оригінального Flutter-репозиторію —
розмір (~300 МБ) робить недоцільним включення в цей архів.

Скопіюйте наступні теки з `assets/pictures/` вашого Flutter-проєкту
**в `shared-assets/pictures/`** (назви й структура вже ідентичні коду):

## 2. Налаштуйте сервер

```bash
cd server
cp .env.example .env
# відредагуйте .env і вкажіть GITHUB_TOKEN
npm install
```

`GITHUB_TOKEN` потрібен лише для збереження/читання хотспотів (клікабельних
зон) через GitHub API — так само, як токен у Cloudflare Worker оригіналу.
Без нього застосунок працюватиме, але хотспоти зберігатимуться лише
локально в браузері (`localStorage`), без синхронізації з GitHub.

## 3. Зберіть клієнт і запустіть

```bash
cd client
npm install
npm run build     # створює client/dist

cd ../server
npm start          # http://localhost:3000
```

### Розробка (hot reload)

```bash
# термінал 1
cd server && npm run dev

# термінал 2
cd client && npm run dev   # http://localhost:5173, проксіює /api і /assets на :3000
```

## Нова сторінка: картки персонажів (3D-моделі, `/skins`)

Окрема сторінка (`client/src/pages/CharacterCardPage.jsx`), яка на основі
файлів **Blockbench `.bbmodel`** (геометрія + анімації) і **PNG-скінів**
рендерить анімовану 3D-модель персонажа у форматі картки-профілю (як на
референсному скріншоті "Профільник").

**Як користуватись:**
1. Відкрийте `/skins` (посилання "Картки персонажів" у меню "Інструменти" на
   головній сторінці)
2. Завантажте файл `.bbmodel` (експортований з [Blockbench](https://www.blockbench.net/))
3. Завантажте PNG-скін — простий режим накладає одне зображення одразу на
   всю модель; якщо модель має кілька текстур-слотів, можна перемкнутись у
   розширений режим і завантажити файл під кожен слот окремо
4. Вкажіть назву, рідкісність і опис — і натисніть "Створити картку"
5. Модель обертається мишею (drag), масштабується колесом; клік по кубу
   виділяє його і показує назву; є перемикачі каркасу/сітки/автообертання,
   слайдер швидкості анімації та показ пивотів кісток

**Технічна реалізація** (`client/src/lib/bbmodel.js`):
- Парсер `.bbmodel`: будує ієрархію кісток/пивотів з `outliner`, геометрію
  кубів з `elements` (per-face UV-мапінг на текстуру, або класичне
  Minecraft-розгортання для елементів без `faces`)
- Плеєр анімацій: лінійна інтерполяція keyframe-ів `position`/`rotation`/
  `scale` (кватерніонна композиція для обертань) з підтримкою `loop`/`once`/`hold`
- Рендер через `three.js` (`client/src/components/ModelViewport.jsx`)

### Два виправлені баги (з референсного прототипу)

**1. Кістки відображались не в тих місцях.** Причина: локальна позиція
кожної pivot-групи рахувалась як `origin - parentOrigin` (сирий зсув у
світових координатах) і напряму ставилась у `.position` дочірньої
`THREE.Group`. Це коректно **лише коли rest-поворот батьківської кістки
дорівнює нулю** — bo three.js додатково обертає позицію дочірнього обʼєкта
на поворот батька при композиції трансформацій, тож будь-яка кістка з
ненульовим `rotation`, що має дітей, зсуває їх убік.

Виправлення: зсув між origin-ами тепер обертається на **обернений
кватерніон акумульованого світового повороту батька**, перш ніж стати
`.position` дочірнього обʼєкта:
```
localPos = inverse(parentWorldQuaternion) * (childOriginWorld - parentOriginWorld)
```
Перевірено на синтетичному прикладі (кістка, повернена на 45°, з дитиною
на відстані 3 одиниці): стара формула давала дитині позицію `(2.12, 10, -2.12)`
замість правильної `(3, 10, 0)` — помітний зсув. Нова формула дає точний
результат незалежно від повороту предків.

**2. Текстура не з'являлась після завантаження.** Причина: код резолвінгу
текстур вимагав точного співпадіння `face.texture` з `uuid`/`id`/`name` у
масиві `model.textures`, а якщо цей масив був порожній (дуже поширений
випадок — модель без вбудованої текстури), завантаження PNG взагалі
блокувалось повідомленням про помилку й ніколи не застосовувалось.

Виправлення: `resolveTextureKey()` тепер надійно резолвить текстуру в кілька
кроків — точне співпадіння → позиційний індекс масиву → якщо нічого не
знайдено, але завантажено рівно одне зображення, воно застосовується до
**всіх** граней моделі. Крім того, завантажений PNG реєструється одразу під
усіма можливими ключами (`uuid`, `name`, `id` кожного текстур-слоту), тому
збіг знаходиться навіть при неоднозначному форматі файлу.

**Обмеження:** лише лінійна інтерполяція анімацій (без bezier/catmullrom
кривих Blockbench), без IK та частинок.

### Виправлення №3 — знайдено на вашому реальному файлі

Ваш `model_-_Converted.bbmodel` (доданий сюди як `samples/model_-_Converted.bbmodel`
для тестів) використовує **інший формат `outliner`**, ніж я закладав спочатку:
кожен вузол там — це лише `{uuid, children}`, а справжні `name`/`origin`/
`rotation` кожної кістки лежать окремо в масиві `groups`, індексованому по
uuid. У вашого файлу це якраз ноги й голова з відчутними rest-поворотами
(`rotation: [2.46, 0.87, -6.92]` для лівої ноги) — тобто саме той випадок,
де стара формула була б помітно неправильною.

Парсер тепер підвантажує `groups` і мерджить дані по uuid, з фолбеком на
inline-поля для файлів старого формату. Перевірив на вашому файлі напряму:
всі 10 кісток лягли на позицію з точністю до 0.0000 від очікуваної (скрипт
порівнював world-позицію кожної pivot-групи з `groups[].origin`).

Заодно додав: якщо `.bbmodel` вже має вбудовану текстуру (`textures[].source`
— base64, як у вашому файлі, там їх аж 4 — по одній на кожен варіант
голови), картка підхоплює її автоматично одразу після вибору файлу, без
потреби окремо завантажувати PNG. У вашому файлі всі 4 варіанти голови
(різні uuid, texture-індекси 0–3) коректно резолвляться кожен у свою
текстуру.
